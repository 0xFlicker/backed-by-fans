### Open findings

#### CHK028 — High: exact current refund minimum can prevent practical cancellation

**Evidence:** Product §Member says to use the “reviewed minimum refund” and to refresh when elapsed time reduces the refund below that minimum. Interface §Cancellation supplies a minimum-refund bound but no deadline or explicit tolerance policy.

**Issue:** If the UI uses the exact current projected refund as its minimum, normal time-based consumption can reduce the amount before inclusion. Repeating the same refresh-and-submit procedure can repeat the failure; refreshing alone does not resolve the moving value. The native action permits choosing a lower minimum, but the first-party requirements do not say how that is chosen and consented to.

**Needed:** Define a workable, user-visible minimum-refund policy and its relationship to quote age. For example, a disclosed owner-approved lower bound, or a time-bounded quote with a conservatively calculated floor and expiry protection. Preserve current-owner and operator authority and do not silently relax the bound. Record a delayed-inclusion acceptance criterion. These are alternatives for requirements resolution, not changes made by this review.

#### CHK036 — High: creator prepayment-limit changes leave enrollment semantics incomplete

**Evidence:** Spec FR-013 requires target validity against the cap and revalidation of current limits. Data Model §Refill calculation defines paid headroom as cap minus remaining paid time. Existing `contracts/src/MembershipTier.sol` allows creator changes through `setMaxPrepaidPeriods`, including below an existing position's remaining paid time.

**Issue:** The documents do not explicitly resolve whether an already-enrolled oversized target is retained and clamped, disabled, or rejected until the owner changes it. They also leave negative headroom implicit when a newly lowered cap is below remaining paid time. “Recheck limits” is insufficient to choose between these outcomes, including what later raising the cap does.

**Needed:** Define enrollment retention, nonnegative available headroom, blocked/partial status and resumption after cap changes. A minimal candidate is to retain owner intent, clamp available paid headroom to zero when already at/above cap, and buy only currently allowed whole periods; make subsequent resumption explicit. This candidate is not yet adopted.

#### CHK037 — High: revoking grants can accelerate authorized spending

**Evidence:** Spec FR-011 includes granted time in the refill target, while §Assumptions preserves creator grant revocation. No cancellation/refill scenario or member disclosure addresses their combination.

**Issue:** Removing granted time from a still-live paid position can reduce remaining time below its target. A permissionless refill can then collect a payment earlier than the holder expected. This follows the combined rules without exploiting an accounting bug and matters to the original concern about creator influence over membership economics.

**Needed:** Explicitly decide whether that acceleration is accepted under the holder's remaining-time authorization. If accepted, require disclosure and an acceptance scenario; otherwise specify the revised grant/refill interaction. Grant-only retirement must still clear enrollment and must never trigger a post-retirement purchase. No new grant policy is inferred by this review.

#### CHK011 — Medium: grant capacity wording is inconsistent across artifacts

**Evidence:** Spec §Edge Cases mentions “granted time consuming capacity,” while Research §4 and Data Model §Refill calculation say grants affect total target/expiration but do not consume the existing paid-time cap.

**Issue:** The plan chooses the existing paid-cap interpretation clearly, but the specification's shorthand permits a different implementation reading.

**Needed:** Clarify the spec's wording: granted time affects remaining-time target and expiration headroom, not the paid-time prepayment cap. Distinguish this from NFT supply occupancy. This is documentation reconciliation of the selected design, not a proposed cap-policy change.

#### CHK038 — Low: paused tier capability enablement is unstated

**Evidence:** Interface §Enrollment and execution explicitly permits target updates while paused; Interface §Creator configuration describes one-way capability enablement without specifying paused eligibility. Spec FR-021 explicitly blocks payments but does not enumerate enablement.

**Issue:** Target-update behavior is resolved; capability enablement remains inferential across the creator and member surfaces.

**Needed:** State whether a creator may enable periodic capability while paused, consistently with allowing non-paying configuration changes and requiring explicit owner enrollment. No funds should move as a side effect either way.

#### CHK039 — Low: cancellation preview behavior after expiration is unspecified

**Evidence:** Data Model §Position enrollment permits stopping an expired-but-unretired NFT. Spec FR-007 disallows cancellation after expiry and Product §State and race handling distinguishes lifecycle states. CancellationPreview lacks an explicit lifecycle/eligibility field, and the interface does not define whether expired/retired requests return status or reject.

**Issue:** Mutating cancellation behavior is clear, but the read contract and corresponding member explanation are incomplete when a position expires between selection and preview.

**Needed:** Specify expired-pending and retired preview outcomes and UI treatment. An unavailable cancellation must not appear as a valid zero-value exit; existing earned-claim access remains available through the appropriate lifecycle reads.
