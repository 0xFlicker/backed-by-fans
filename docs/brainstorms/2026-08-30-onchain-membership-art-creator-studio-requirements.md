# Backed By Fans Onchain Membership Art and Creator Studio

## Summary

Every membership is one desirable onchain artwork. Its metadata contains one canonical `image`: a
self-contained SVG generated by a protocol-approved renderer. There is no `animation_url`, remote
media mode, gateway resolver, or hosted asset dependency.

Creator media is optional input material, never a reference. A creator chooses a JPEG or PNG from
their computer or pastes actual image bytes. The Studio decodes, crops, resizes, strips metadata,
and re-encodes the image locally. The creator approves those exact transformed bytes, pays to store
them in immutable Robinhood Chain contract code, and publishes a tier that pins the store. The
renderer reads the bytes and embeds them as a data URI inside the canonical SVG.

The initial renderer ships six finished engines. The protocol factory also owns an append-only
renderer registry so governance can publish and enable additional renderer implementations without
silently changing artwork already issued by an existing tier.

## Product Principles

- **Onchain means onchain.** Metadata, SVG, generated composition, and optional transformed image
  bytes require no web server, gateway, or third-party storage network.
- **The SVG is the NFT artwork.** It is not a thumbnail for an HTML application and has no hidden
  second visual identity.
- **Generated art stands on its own.** A tier without creator media must look intentional and
  collectible at marketplace-thumbnail size.
- **Uploaded images become material.** The renderer masks, crops, blends, and layers the embedded
  raster within the same composition.
- **Creators choose permanence deliberately.** The Studio shows the exact processed image and
  contract-rendered composition before either transaction.
- **Surprise Me is first-class.** Creators may reroll seeds and bounded controls locally until the
  result feels worth publishing.
- **Expiration changes mood, not worth.** Active and afterglow preserve token geometry and both
  remain desirable.
- **Renderer evolution is additive.** New versions may be appended for new tiers; published tiers
  remain pinned to their original renderer address and runtime code hash.

## Art Direction

The family combines warm live-room energy, tactile print texture, dimensional layering, visible
supporter presence, and confident editorial composition. It avoids generic neon crypto gradients,
interchangeable sci-fi HUDs, arbitrary particle fields, and placeholder geometric noise.

The founding renderer contains six engines:

- **STACK** — monumental offset planes derived from the Backing Stack mark;
- **CHORUS** — supporter lights arranged as a crowd around the creator;
- **LOOM** — woven signal ribbons with media revealed through selected openings;
- **BLOOM** — radial growth, stage-light halos, and luminous archival traces;
- **MARQUEE** — oversized editorial typography, registration marks, and poster rhythm;
- **AFTERIMAGE** — image-forward masks, repetition, duotone tension, and negative space.

Each engine uses the same bounded protocol art record but interprets its controls through a distinct
visual grammar. Token ID, chain ID, immutable tier identity, collection seed, and creator settings
determine the composition.

## Key Flows

### Create generated-only artwork

1. The Studio starts with a strong engine configuration and no media.
2. The creator tunes controls or rerolls with Surprise Me.
3. Contract-backed previews show representative token IDs in active and afterglow states.
4. The creator publishes the tier in one transaction.
5. Every token returns a self-contained SVG with no network dependency.

### Add an image from a computer

1. The creator chooses a local JPEG or PNG.
2. The Studio validates source size and dimensions before decode.
3. The browser decodes, applies orientation and crop, resizes, strips metadata by re-encoding, and
   produces a bounded JPEG or PNG candidate.
4. Preview, gas estimate, storage write, and final tier configuration all use the same byte array.
5. The wallet stores the candidate in the creator-scoped media registry.
6. Canonical reads confirm store address, MIME, length, digest, creator, and runtime code hash.
7. The Studio publishes the tier with that confirmed record.

### Paste an image

Clipboard image bytes enter the exact same processing function as a selected file. Clipboard text,
URLs, HTML, and remote references are not media inputs. If the clipboard does not contain a JPEG or
PNG file item, the Studio explains what to paste and does not mutate the draft.

### Recover after media storage

If storage succeeds but tier publication does not, the confirmed store remains discoverable through
the creator's onchain media library. Recovery is a domain read, not custom transaction-history
reconstruction.

### Add a renderer version

1. Protocol governance deploys an immutable renderer implementing the fixed schema.
2. Governance registers it; the factory appends a version and snapshots its runtime code hash in a
   disabled state.
3. The release passes contract, gas, response-size, consumer, and visual review.
4. Governance enables the version for future tier creation.
5. A frontend release may expose renderer-specific controls, but the protocol can already pin and
   enforce the new version.
6. Disabling a renderer blocks new tiers only; existing tiers keep their pinned implementation.

## Requirements

### Canonical metadata and art

- `tokenURI` returns a base64 `data:application/json` URI.
- Metadata contains one base64 `data:image/svg+xml` `image` value.
- Metadata has no `animation_url`, remote media URL, script, or loader state.
- The SVG contains all CSS, generated geometry, typography, and optional raster bytes inline.
- Marketplace and first-party previews decode the same `image`; there is no parallel renderer.
- Active and afterglow preserve stable geometry for a token.
- Art configuration is immutable after tier publication.
- Engine identifiers are extensible `uint16` values, not a six-value protocol enum.
- Bounded controls cover palette, intensity, density, symmetry, typography, image placement, grain,
  media mix, and three engine-specific values.
- Every admitted value renders without revert, stays bounded, and remains deterministic.
- Surprise Me uses browser cryptographic randomness and preserves individually locked controls.

### Image transformation and storage

- Accepted source interactions are local file selection and clipboard image paste.
- Accepted onchain formats are JPEG and PNG.
- Source limits are enforced before decode; output limits are enforced after encode.
- EXIF orientation is normalized before decode and applied exactly once by the Studio.
- Re-encoding removes source metadata and yields one square output candidate.
- Creators can adjust dimension, JPEG quality, PNG purpose, crop focal point, and fit.
- The renderer-safe maximum is 90 KiB unless a coordinated measured release lowers it.
- Exact candidate bytes are shared by preview, quote, write, digest, and reconciliation.
- Storage uses `STOP || payload` immutable runtime code and records creator, MIME, length, digest,
  and runtime code hash.
- Duplicate creator uploads reuse the same creator-scoped store.
- Official tier creation rejects unregistered, foreign, mutated, or mismatched records.
- Failure to fit the onchain bound is actionable; there is no remote fallback.

### Renderer registry

- The factory owns an append-only `uint32` renderer version sequence.
- A renderer exposes schema, renderer name, engine count, engine names, configuration validation,
  SVG preview, metadata preview, and production metadata rendering.
- Registration snapshots implementation and runtime code hash and starts disabled, except the
  founding constructor registration.
- Only protocol ownership may register or enable versions.
- Tier creation requires an enabled renderer with unchanged runtime code.
- Each tier stores renderer version, address, and runtime code hash and verifies code identity before
  rendering.
- Disablement never rewrites or disables an existing tier.
- Proxy renderers and mutable implementation indirection are not admissible.

### Transaction boundary

- Application code simulates each write and passes the exact request to the wallet.
- wagmi/viem own submission, receipts, replacement, cancellation, and polling.
- The application reconciles only a supplied successful receipt against canonical reads.
- New media and tier publication are two explicit wallet transactions.
- A confirmed creator media store can be reused without a storage transaction.

### Deployment and evidence

- The disposable testnet generation receives no adapter or migration path.
- Anvil and target-chain fork deployment use Robinhood's larger code/initcode envelope.
- Public testnet broadcast remains behind the interactive operator-password gate.
- Generated bindings become canonical only from a fully verified deployment record.
- Every founding engine is visually inspected for token IDs 1, 7, and 42, generated and onchain
  media, active and afterglow, at thumbnail and full size.

## Acceptance Examples

- Generated STACK metadata has one self-contained SVG and no external resource.
- A pasted PNG is transformed, stored on Robinhood Chain, and embedded as
  `data:image/png;base64` inside the SVG.
- A 20 MiB or oversized-dimension source is rejected before decode.
- A candidate over 90 KiB asks for lower size/quality and never suggests remote hosting.
- Storage succeeds while tier creation is abandoned; the media appears in the creator's verified
  onchain library on reload.
- Governance registers renderer version 2; version 1 tiers retain their renderer identity while only
  enabled versions may serve new tiers.
- An expired membership changes to afterglow without changing deterministic geometry.

## Scope Boundaries

In scope: renderer registry, founding renderer, SVG metadata, browser image transformation,
creator-paid Robinhood storage, Studio controls, exact previews, two-stage publication, local/fork
deployment proof, visual review, and gated public testnet release.

Out of scope: moderation and frontend suppression, Arweave, IPFS, remote URLs, hosted media,
`animation_url`, HTML/JavaScript NFT documents, video/audio, arbitrary creator code, multi-store
images, renderer proxies, migration adapters, and mainnet broadcast.

## Success Criteria

- Generated-only memberships are immediately recognizable and desirable.
- Creator-media memberships contain those exact transformed bytes on Robinhood Chain and in SVG.
- No media identity or rendering dependency points offchain.
- Six engines and both states are deterministic, bounded, legible, and visually distinct.
- The protocol can append renderer versions while preserving existing token identity.
- The Studio makes permanence, byte size, and transaction sequence clear before signing.
